Rust String / &str / Lifetime 완벽 가이드

문자열의 세 얼굴 — String, str, &str — 과 그 뒤에 따라붙는 라이프타임을, 메모리 모델부터 시작해 75개 이상의 예제로 점진적으로 익힙니다. 자바 개발자가 가장 어려워하는 NLL, 생략 규칙, HRTB까지 빠짐없이 다룹니다.

이 가이드를 읽는 법 각 예제 우측 하단의 ▶ 실행 버튼으로 Wandbox에서 직접 컴파일·실행할 수 있습니다. 실행 환경은 rust-1.82.0 (edition 2021)입니다. 에러를 의도한 예제는 컴파일 에러가 출력되며, 그것이 학습 포인트입니다.

먼저 한 줄 정리

타입소유저장 위치크기변경 가능?
String소유힙가변예 (가변일 때)
&str빌림힙/정적/스택 어디든고정 (fat ptr)아니오
str——알 수 없음 (DST)—
&String빌림힙 가리키는 포인터포인터 1개아니오

자바와의 결정적 차이 두 가지 ① 자바 String은 불변, GC가 관리 — Rust String은 가변, 스코프 종료 시 자동 해제. ② 자바에는 "라이프타임"이 없다 (GC가 다 해결). Rust는 컴파일 시점에 모든 참조의 유효 기간을 추적한다.

Part 0. 메모리 모델 기초

String과 &str의 차이는 "어디 사느냐"와 "누가 책임지느냐"의 차이다. 이 둘을 이해하려면 먼저 Rust 프로그램이 사용하는 세 영역 — 스택, 힙, 정적 영역(.rodata) — 을 머릿속에 그려둬야 한다.

0.1 스택 / 힙 / 정적 영역 한눈에

위 그림에서 핵심 두 가지를 짚는다:

  • &str (위쪽 lit)는 두 칸짜리 빌림이다. 어떤 데이터를 가리키기만 할 뿐, 자기가 들고 있지 않다.
  • String (아래쪽 s)는 세 칸짜리 소유자다. ptr·len·cap을 들고 있고, 힙 데이터의 수명을 책임진다.

0.1세 영역에 각각 사는 값

스택 정수, 정적 영역을 빌린 &str, 힙을 가진 String을 한자리에서.
fn main() {
    let stack_int: i32 = 42;                       // 스택에 4바이트
    let static_lit: &str = "Hello";              // 정적 영역을 빌린 fat pointer
    let heap_str: String = String::from("World");  // 힙에 실제 데이터 + 스택에 핸들

    println!("stack_int = {}", stack_int);
    println!("static_lit = '{}'  (len={})", static_lit, static_lit.len());
    println!("heap_str   = '{}'  (len={}, cap={})", heap_str, heap_str.len(), heap_str.capacity());

    // 타입 크기 — &str과 String이 스택에서 차지하는 크기
    println!("size_of::<&str>()   = {}", std::mem::size_of::<&str>());
    println!("size_of::<String>()  = {}", std::mem::size_of::<String>());
    println!("size_of::<i32>()     = {}", std::mem::size_of::<i32>());
}
출력의 핵심 64비트 시스템에서 &str는 16바이트(ptr 8 + len 8), String는 24바이트(ptr 8 + len 8 + cap 8). 이 숫자는 스택 위의 크기다. 실제 문자 데이터는 힙 또는 정적 영역에 따로 있다.

0.2 정적 영역 — 문자열 리터럴이 사는 곳

"Hello" 같은 문자열 리터럴은 컴파일 결과물(실행 바이너리)의 읽기 전용 데이터 섹션(.rodata)에 들어간다. 프로그램이 메모리에 적재되면 이 섹션은 프로세스가 끝날 때까지 살아있다. 그래서 리터럴을 가리키는 &str는 항상 &'static str 타입이다 (Part 8에서 다시).

0.2String이 자라면서 힙 재할당이 일어나는 모습

초기 capacity가 0인 String에 문자를 추가하며 capacity가 어떻게 늘어나는지 본다.
fn main() {
    let mut s = String::with_capacity(0);
    println!("초기      : len={:2}, cap={:2}, '{}'", s.len(), s.capacity(), s);
    for chunk in ["He", "llo", ", ", "world", "! ", "Rust is here."] {
        s.push_str(chunk);
        println!("'{}' 추가: len={:2}, cap={:2}, '{}'",
                 chunk, s.len(), s.capacity(), s);
    }
}
capacity 증가 정책 String(내부 Vec<u8>)의 정책: 첫 할당에서 최소 8바이트로 점프하고(요소 크기가 1바이트인 경우), 그 뒤로는 가득 찰 때마다 두 배씩 늘어난다. 그래서 한 번의 push는 평균적으로 O(1)이 된다 (amortized O(1)). 재할당 시에는 새 버퍼 할당 + 기존 데이터 복사 + 옛 버퍼 해제가 일어난다.

0.3 스코프 종료 = 자동 해제

자바와 가장 다른 점이다. Rust는 GC가 없는 대신 변수가 스코프를 벗어나는 순간 Drop trait의 drop()이 자동 호출되어 힙 메모리가 해제된다. 문자열 리터럴(정적 영역)은 해제되지 않는다 — 영원히 산다.

0.3안쪽 스코프 종료 시 String이 drop

커스텀 타입에 Drop을 구현해서 정확히 언제 해제되는지 눈으로 본다.
struct Tag(&'static str);
impl Drop for Tag {
    fn drop(&mut self) {
        println!("  [drop] {}", self.0);
    }
}

fn main() {
    println!("바깥 시작");
    let outer = Tag("outer");
    {
        let inner_s = String::from("inner string");
        let _inner_tag = Tag("inner_tag");
        println!("  안쪽: '{}'", inner_s);
    } // ← 여기서 _inner_tag, inner_s 가 역순으로 drop
    println!("바깥 끝 (outer는 아직 살아있음)");
    let _ = &outer; // 일부러 사용해서 일찍 drop 방지
} // ← main 끝에서 outer drop
drop 순서 = 선언의 역순 한 스코프에서 여러 변수가 drop될 때는 나중에 선언된 것이 먼저 drop된다. 이 규칙은 라이프타임 추론(Part 5)에서 의외로 자주 사용된다.

Part 1. String — 힙 소유 문자열

String은 UTF-8 바이트 시퀀스를 소유하는 가변 힙 버퍼다. 자바의 StringBuilder에 가깝다 (자바 String은 불변이라 다르다). 내부는 Vec<u8>의 얇은 래퍼 — 즉 ptr·len·cap 세 워드.

1.1 String 생성 방법들

같은 문자열을 만드는 데에도 네다섯 가지 방법이 있다. 각 함수가 무엇을 반환하는지가 다르다.

표현반환특징
String::new()String힙 할당 없음 (cap=0)
String::from("a")String리터럴 복사해 힙에 새 버퍼
"a".to_string()String위와 동일 결과
"a".to_owned()String위와 동일 결과 (의도가 더 명확)
String::with_capacity(16)String힙에 16바이트 예약, len=0
format!("a{}", x)String매크로로 즉시 포맷

1.1여섯 가지 방법, 같은 결과

표의 6가지를 한 번에 실행해 비교한다.
fn main() {
    let a: String = String::new();
    let b: String = String::from("hello");
    let c: String = "hello".to_string();
    let d: String = "hello".to_owned();
    let e: String = String::with_capacity(16);
    let f: String = format!("hel{}", "lo");

    println!("a = '{}' (len={}, cap={})", a, a.len(), a.capacity());
    println!("b = '{}' (len={}, cap={})", b, b.len(), b.capacity());
    println!("c = '{}' (len={}, cap={})", c, c.len(), c.capacity());
    println!("d = '{}' (len={}, cap={})", d, d.len(), d.capacity());
    println!("e = '{}' (len={}, cap={})", e, e.len(), e.capacity());
    println!("f = '{}' (len={}, cap={})", f, f.len(), f.capacity());
}

1.2소유권 이동 — String은 Copy가 아니다

기본 정수와 달리 String은 대입/전달 시 소유권이 옮겨간다.
fn main() {
    let s1 = String::from("Rust");
    let s2 = s1;            // s1의 소유권이 s2로 이동 (move)
    // println!("{}", s1);  // 컴파일 에러: borrow of moved value
    println!("s2 = {}", s2);

    // 비교: i32는 Copy 트레이트라 그냥 복사된다
    let n1: i32 = 42;
    let n2 = n1;
    println!("n1 = {}, n2 = {}", n1, n2); // 둘 다 사용 가능
}

1.2 가변성과 push 계열

String은 let mut 으로 선언하면 내부 바이트를 수정할 수 있다. 네 가지 추가 메서드가 자주 쓰인다.

메서드인자 타입설명
push(c)char문자 1개 추가
push_str(&s)&str슬라이스 추가 (소유권 이동 없음)
+= "..."&strpush_str의 단축형
insert_str(i, &s)usize, &str특정 바이트 위치에 삽입

1.3네 가지 변경 메서드

push, push_str, +=, insert_str을 차례로.
fn main() {
    let mut s = String::from("Ru");
    s.push('s');                 // char 1개
    s.push('t');
    println!("after push       : {}", s);   // Rust

    s.push_str(" lang");          // &str 추가
    println!("after push_str   : {}", s);   // Rust lang

    s += " 2025";                  // += 는 push_str과 같다
    println!("after +=         : {}", s);   // Rust lang 2025

    s.insert_str(0, "[ ");         // 0번 바이트 위치에 삽입
    s.push_str(" ]");
    println!("after insert_str : {}", s);   // [ Rust lang 2025 ]
}

1.3 capacity와 재할당 비용

매번 한 글자씩 push하면 cap이 가득 찰 때마다 새 힙 버퍼 할당 + 기존 데이터 복사 + 옛 버퍼 해제가 일어난다. 미리 with_capacity로 충분한 크기를 잡아두면 이를 피할 수 있다.

1.4cap이 변하는 순간 추적

capacity()가 변하는 지점만 출력 → 재할당이 일어난 횟수를 센다.
fn main() {
    let mut s = String::new();
    let mut last_cap = s.capacity();
    let mut realloc_count = 0;
    println!("start: len=0, cap={}", last_cap);
    for i in 0..32 {
        s.push('a');
        let cap = s.capacity();
        if cap != last_cap {
            realloc_count += 1;
            println!("  [realloc #{}] i={:2}: cap {} → {}", realloc_count, i, last_cap, cap);
            last_cap = cap;
        }
    }
    println!("end  : len={}, cap={}, realloc 횟수={}", s.len(), s.capacity(), realloc_count);
}

1.5with_capacity로 재할당 0회

미리 cap을 충분히 잡아두면 같은 작업에서 재할당이 일어나지 않는다.
fn main() {
    let mut s = String::with_capacity(64);
    let initial_cap = s.capacity();
    for _ in 0..32 { s.push('a'); }
    println!("초기 cap = {}, 최종 cap = {} (변화 없음 = 재할당 0회)",
             initial_cap, s.capacity());
}

1.4 + 연산자, format!, 그리고 그 차이

String + &str 은 가능하지만 String + String 은 안 된다. 왜인가? String의 Add 구현이 다음 시그니처이기 때문이다: 

impl Add<&str> for String {
    type Output = String;
    fn add(self, other: &str) -> String { ... }
}

① 왼쪽 String의 소유권을 가져가고 ② 오른쪽은 &str만 받는다. 그래서 a + b에서 a는 사라지고, b는 String이면 &b로 빌려서 넘겨야 한다 (Deref로 &str이 됨).

1.6+ 연산자의 소유권 동작

왼쪽은 사라지고 오른쪽은 살아남는다.
fn main() {
    let hello = String::from("Hello, ");
    let world = String::from("World!");
    let combined = hello + &world;    // hello는 move, world는 빌림
    println!("combined = {}", combined);
    // println!("hello = {}", hello); // 에러: hello는 이미 move됨
    println!("world  = {} (여전히 살아있음)", world);
}

1.7format! — 모두 빌리고 새 String 반환

+와 달리 어느 쪽도 소유권을 잃지 않는다. 다인자 조합도 자연스럽다.
fn main() {
    let name = String::from("베이스한");
    let lang = String::from("Rust");
    let year = 2025;

    // 모두 빌리기만 함
    let msg = format!("{}님은 {} {}년차 개발자", name, lang, year);
    println!("{}", msg);
    println!("name = {}, lang = {} (둘 다 살아있음)", name, lang);
}

1.5 인덱싱 불가 — UTF-8과의 정직한 타협

Rust에서 s[0] 같은 정수 인덱싱은 컴파일 에러다. 왜냐하면 UTF-8에서 한 바이트가 한 글자가 아니기 때문이다. "한"은 3바이트, "a"는 1바이트, 이모지는 4바이트 등. 대신 네 가지 뷰가 제공된다.

메서드반환단위
.bytes()Bytes 반복자UTF-8 바이트(u8)
.chars()Chars 반복자유니코드 코드 포인트(char)
.char_indices()CharIndices(바이트 인덱스, char)
.as_bytes()&[u8]바이트 슬라이스 (인덱싱 가능)

1.8s[0]은 에러, 네 가지 뷰는 OK

한글이 섞인 문자열에서 바이트와 char를 비교한다.
fn main() {
    let s = String::from("Hi한글");
    // let c = s[0]; // 에러: the type `String` cannot be indexed by `{integer}`

    println!("문자열       : '{}'", s);
    println!("바이트 개수  : {}", s.len());        // 8 (H i 한[3] 글[3])
    println!("문자 개수    : {}", s.chars().count()); // 4

    print!("바이트들  : ");
    for b in s.bytes() { print!("{:3} ", b); }
    println!();

    print!("chars()   : ");
    for c in s.chars() { print!("'{}' ", c); }
    println!();

    print!("char_indices(): ");
    for (i, c) in s.char_indices() { print!("({},'{}') ", i, c); }
    println!();
}

use std::fmt;

struct Point { x: i32, y: i32 }

    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

#[derive(Debug)]
struct Tagged { name: String, count: u32 }

fn main() {
    let p = Point { x: 3, y: 4 };
    let t = Tagged { name: "rust".into(), count: 42 };

    println!("Display: {}",   p);          // (3, 4)
    println!("Debug  : {:?}", t);          // Tagged { name: "rust", count: 42 }
    println!("Pretty : {:#?}", t);          // 줄바꿈된 Debug

    println!("[{:>10}]",   "right");        // [     right]
    println!("[{:<10}]",   "left");         // [left      ]
    println!("[{:^10}]",   "center");       // [  center  ]
    println!("[{:*>10}]",  "pad");          // [*******pad]

    // 숫자 진수
    println!("hex   : {:x}",   255);        // ff
    println!("HEX   : {:08X}", 255);        // 000000FF
    println!("oct   : {:o}",   255);        // 377
    println!("bin   : {:b}",   255);        // 11111111

    println!("scien : {:.2e}", 12345.6);    // 1.23e4

    // 위치 인자
    println!("{1} {0}", "world", "hello");  // hello world

    // 명명 인자
    println!("{name}={val}", name = "n", val = 42);
}

Part 2. &str — 빌린 문자열 슬라이스

&str는 "이미 어딘가에 있는 UTF-8 바이트 시퀀스의 일부를 빌린 뷰"다. 소유하지 않는다. 들고 다니는 건 두 개: 시작 포인터와 길이. 이것을 fat pointer라 한다.

2.1 문자열 리터럴의 정체

소스 코드에 적힌 "hello"는 컴파일 시점에 .rodata에 박히고, 그것을 가리키는 &str 핸들이 만들어진다. 이 핸들의 타입은 정확히 &'static str 이다. 라이프타임이 'static' — 즉 프로그램 전체 — 인 이유는 .rodata가 끝까지 살아있기 때문이다.

fn main() {

Part 3. str / &str / &String 구별

세 가지가 헷갈리는 진짜 이유는 str 자체를 직접 쓸 일이 거의 없기 때문이다. 이번 파트에서 셋을 명확히 갈라낸다.

&String은 두 번 따라가야 데이터에 닿는다. &str는 한 번. 함수 매개변수로 &str를 선호하는 이유다.

3.1 str는 DST — 직접 변수에 담을 수 없다

str는 컴파일러가 크기를 알 수 없는 타입이다 (Dynamically Sized Type, DST). "hello"는 5바이트, "hi"는 2바이트 — 같은 str이라도 크기가 다르다. Rust는 모든 변수의 크기를 컴파일 시점에 알아야 하므로, str를 직접 변수에 담는 건 불가능하다. 반드시 어떤 종류의 참조나 박스를 거쳐야 한다.

3.1str을 직접 담으려 하면 에러

의도된 컴파일 에러. 메시지에서 "doesn't have a size known at compile-time"을 확인한다.
fn main() {
    // 의도된 에러: str은 Sized가 아니다
    let x: str = *"hello";
    println!("{}", x);
}

3.2 &String 은 거의 안 쓰는 이유

&String은 "String의 핸들을 가리키는 포인터"다. 그림에서 보듯 데이터에 도달하려면 두 번 따라가야 한다. 함수 매개변수로 &String을 받으면 호출자가 반드시 String을 들고 있어야 하므로 호출 가능 범위가 좁아진다. 그래서 거의 항상 &str를 받는다.

3.2&String 받는 함수의 한계

&String을 받는 함수에는 리터럴을 그대로 넘길 수 없다.
fn takes_string_ref(s: &String) {
    println!("len = {}", s.len());
}
fn takes_str(s: &str) {
    println!("len = {}", s.len());
}

fn main() {
    let owned = String::from("hello");

    takes_string_ref(&owned);   // OK
    takes_str(&owned);          // OK (&String → &str 자동 변환)
    takes_str("literal");        // OK (리터럴은 &'static str)

    // takes_string_ref("literal"); // 에러! 리터럴은 &str이지 &String이 아님
}
실용 규칙 읽기만 할 거면 매개변수 타입을 &str로 잡는다. 가변 변경이 필요하면 &mut String, 소유권이 필요하면 String을 받는다. &String은 거의 안 쓴다.

3.3 Deref 강제 변환 — &String 이 &str 처럼 동작하는 마법

String은 Deref<Target = str> 트레이트를 구현한다. 그래서 &String이 필요한 자리에 있어야 할 &str가 자동으로 만들어진다. 메서드 호출 시에도 마찬가지로 String 위에서 &str의 메서드를 그대로 쓸 수 있다.

3.3Deref 강제 변환 시연

컴파일러가 자동으로 &String → &str를 끼워 넣는다.
fn count_chars(s: &str) -> usize {
    s.chars().count()
}

fn main() {
    let owned = String::from("한글");

    // 다음 4줄은 모두 같은 결과 — 컴파일러가 알아서 변환
    println!("{}", count_chars(&owned));
    println!("{}", count_chars(owned.as_str()));
    println!("{}", count_chars(&owned[..]));
    println!("{}", count_chars(&*owned));     // 명시적 deref (잘 안 씀)
}

3.4 Box<str> — 잘 안 보이는 형태

String의 cap이 더 이상 필요 없을 때 (값을 만든 뒤 변경하지 않을 때) Box<str>로 줄이면 24바이트 → 16바이트로 핸들이 작아진다. String은 가변, Box<str>은 고정 길이 힙 소유.

3.4String을 Box<str>로 줄이기

생성 후 변경하지 않을 문자열에 메모리 절약 패턴.
use std::mem::size_of;

fn main() {
    let s: String = String::from("hello");
    let b: Box<str> = s.into_boxed_str();   // cap 정보 폐기

    println!("Box<str> = '{}'", b);
    println!("len = {}", b.len());
    println!("size_of::<String>()    = {}", size_of::<String>());
    println!("size_of::<Box<str>>()  = {}", size_of::<Box<str>>());

    // Box<str>도 &str로 빌릴 수 있다 (Deref 동일)
    let view: &str = &b;
    println!("view = '{}'", view);
}

3.5 비교 연산 — 다른 타입끼리 ==이 되는 이유

String == &str 이 가능한 이유는 String이 PartialEq<str>, PartialEq<&str> 등을 여러 개 구현하기 때문이다. 일반 사용자 입장에선 그냥 "문자 내용이 같으면 같음" 으로 작동한다.

3.5가능한 모든 조합의 == 비교

String/&str/리터럴 사이 비교가 다 된다.
fn main() {
    let owned   = String::from("rust");
    let slice: &str = "rust";
    let other   = String::from("rust");

    println!("String == &str           : {}", owned == slice);
    println!("&str == String           : {}", slice == owned);
    println!("String == String          : {}", owned == other);
    println!("String == 리터럴(&str)   : {}", owned == "rust");
    println!("리터럴 == String          : {}", "rust" == owned);
    println!("&str == &str            : {}", slice == "rust");

    // 정렬도 가능
    let mut v = vec!["banana", "apple", "cherry"];
    v.sort();
    println!("sorted: {:?}", v);
}

3.6주의 — &&String 같은 다중 참조도 통한다

메서드 호출 시 컴파일러는 필요한 만큼 자동 deref한다 (auto-deref).
fn main() {
    let s = String::from("abc");
    let r: &String = &s;
    let rr: &&String = &r;
    let rrr: &&&String = &rr;

    // 메서드 호출 시 자동으로 deref 됨
    println!("len through &&&String = {}", rrr.len());
    println!("upper = {}", rrr.to_uppercase());

    // 명시적으로도 가능
    println!("explicit deref: {}", ***rrr);
}

Part 4. 함수 매개변수 패턴

문자열을 함수에 넘기는 방법은 네 가지다. 어떤 것을 쓰느냐가 함수의 호출 가능 범위와 효율을 결정한다.

매개변수 타입호출자 의미언제 쓰는가
&str읽기만 빌려줌읽기만 할 때 (대부분)
&mut String가변 빌려줌함수가 String을 변경할 때
String소유권 넘김함수가 보관하거나 변형 후 반환할 때
&StringString 핸들 빌려줌거의 안 씀 (3.2에서 본 이유)

4.1 &str 받기 — 가장 유연하다

리터럴, String, Box<str>, 슬라이스 — 모두 받을 수 있다.

4.1&str 매개변수가 받는 다섯 가지 호출

한 함수에 다양한 형태로 호출.
fn word_count(s: &str) -> usize {
    s.split_whitespace().count()
}

fn main() {
    let owned = String::from("one two three");
    let boxed: Box<str> = Box::from("a b c d");
    let slice = "i  am  whitespaced";

    println!("리터럴       : {}", word_count("hello rust world"));
    println!("&String      : {}", word_count(&owned));
    println!("String.as_str: {}", word_count(owned.as_str()));
    println!("&owned[..]   : {}", word_count(&owned[..]));
    println!("Box<str>     : {}", word_count(&boxed));
    println!("&str 변수    : {}", word_count(slice));
}

4.2 String 받기 — 소유권 이동

함수 내에서 보관하거나 (구조체 필드에 넣거나) 변형해 새 String을 만들 때 쓴다. 호출자는 변수를 잃는다.

4.2String 받아서 보관하기

호출 후엔 원래 변수를 쓸 수 없다.
struct User { name: String }

fn create_user(name: String) -> User {
    User { name }   // name을 그대로 가져가서 필드에 넣는다
}

fn main() {
    let n = String::from("Alice");
    let u = create_user(n);
    println!("user.name = {}", u.name);
    // println!("{}", n); // 에러: n은 move됨
}

4.3 &String 안티패턴

이미 3.2에서 본 이야기. 한 번 더 명시적으로 — 이렇게 쓰지 마라.

4.3&String을 받으면 호출 형태가 좁아진다

의도된 컴파일 에러 비교.
fn anti(s: &String) {
    println!("{}", s);
}
fn good(s: &str) {
    println!("{}", s);
}

fn main() {
    let owned = String::from("rust");
    anti(&owned);    // OK
    good(&owned);    // OK
    good("literal"); // OK
    anti("literal"); // 에러: expected `&String`, found `&str`
}

4.4 String 반환

새로 만든 문자열을 호출자에게 넘기는 가장 일반적인 방법.

4.4새 String을 만들어 반환

소유권이 호출자에게 이동.
fn greet(name: &str) -> String {
    format!("Hello, {}!", name)
}

fn shout(s: &str) -> String {
    s.to_uppercase()
}

fn main() {
    let msg = greet("Rust");
    let loud = shout(&msg);
    println!("{}", msg);
    println!("{}", loud);
}

4.5 &str 반환 — 라이프타임 미리보기

참조를 반환하면 컴파일러가 묻는다: "그 참조가 누구의 데이터를 가리키지?" 이 질문에 답하는 게 라이프타임이다 (Part 5에서 본격). 미리 두 가지 흔한 패턴만 본다.

4.5입력에서 잘라낸 &str 반환

반환 슬라이스는 입력 슬라이스의 일부 — 같은 라이프타임을 갖는다.
fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(i) => &s[..i],
        None    => s,
    }
}

fn main() {
    let sentence = String::from("Hello Rust world");
    let w = first_word(&sentence);
    println!("first word = '{}'", w);

    // 직접 리터럴에도
    println!("from literal = '{}'", first_word("foo bar baz"));
}

4.6 &mut String — 함수가 직접 변경

함수가 호출자의 String을 그 자리에서 변경하고 싶을 때.

4.6&mut String으로 in-place 변형

함수 호출 후에도 변수는 그대로 사용 가능 (소유권이 안 바뀜).
fn append_bang(s: &mut String) {
    s.push('!');
}

fn surround(s: &mut String, left: &str, right: &str) {
    s.insert_str(0, left);
    s.push_str(right);
}

fn main() {
    let mut greeting = String::from("hi");
    append_bang(&mut greeting);
    surround(&mut greeting, "[ ", " ]");
    println!("{}", greeting);   // [ hi! ]
}
매개변수 선택 결정 트리 ① 함수가 값을 보관/소비하나? → String. ② 함수가 변경하나? → &mut String. ③ 그 외 (읽기 뿐) → 무조건 &str.

Part 5. 라이프타임 입문

라이프타임은 참조가 가리키는 데이터가 그 참조보다 오래 살아있다는 사실을 컴파일러가 검증하는 도구다. 자바는 GC가 이걸 런타임에 해주지만, Rust는 컴파일 시점에 정적으로 해결한다.

5.1 댕글링 참조 — 컴파일러가 막는 것

가장 단순한 라이프타임 위반. 함수 안에서 만든 String의 참조를 반환하면, 함수가 끝나는 순간 그 String이 drop되어 참조가 허공을 가리키게 된다. Rust는 이를 컴파일 시점에 잡는다.

5.1댕글링 참조 시도 — 컴파일 에러

의도된 에러 E0515 (returns a reference to data owned by current function).
fn dangle() -> &'static String {
    let s = String::from("inner");
    &s   // s는 함수 끝에서 drop. 그 참조를 반환할 수 없다.
}

fn main() {
    let r = dangle();
    println!("{}", r);
}

5.2 'a 문법

라이프타임 매개변수는 ' + 소문자 이름이다. 관례적으로 'a, 'b, 'static 같은 이름을 쓴다. 함수 시그니처에 한 번, 매개변수와 반환 타입에 또 한 번 쓴다.

fn f<'a>(x: &'a str) -> &'a str { ... }
//   ─┬─  ─┬─        ─┬─
//   선언  사용       사용 (반환이 x와 같은 'a 만큼 산다)

5.2가장 단순한 'a 함수

입력 라이프타임을 그대로 반환에 묶는다 (사실 이건 생략 가능 — Part 6).
fn echo<'a>(s: &'a str) -> &'a str {
    s
}

fn main() {
    let owned = String::from("hello");
    let r: &str = echo(&owned);
    println!("{}", r);
}

5.3 longest — 두 입력의 라이프타임 묶기

The Rust Book의 고전 예제. 두 입력 중 어느 쪽이 반환될지 컴파일러가 알 수 없으므로 둘 다 같은 'a여야 한다고 선언한다. 그러면 반환값은 둘 중 더 짧은 쪽만큼 산다.

5.3longest — 두 입력 라이프타임 통일

두 매개변수에 같은 'a를 붙인다.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let s1 = String::from("long string is long");
    {
        let s2 = String::from("short");
        let r = longest(&s1, &s2);
        println!("longest = '{}'", r);
    }
}

5.4 입력보다 짧은 반환 — 라이프타임 위반

반환을 외부 스코프에서 쓰려는데 둘 중 한 입력이 그보다 짧으면 컴파일 에러.

5.4짧은 입력 때문에 외부에서 못 씀 — 컴파일 에러

의도된 에러 E0597.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let s1 = String::from("long string is long");
    let result;
    {
        let s2 = String::from("short");
        result = longest(&s1, &s2);
    } // s2 drop
    println!("{}", result); // s2가 죽은 뒤 result를 쓰려 함 → 에러
}

5.5 NLL (Non-Lexical Lifetimes) — 자바 개발자가 가장 헷갈리는 부분

예전 Rust에선 빌림이 스코프 끝까지 유지됐다. 지금은 다르다. 마지막으로 사용된 지점까지만 빌림이 유지된다. 이게 NLL이다. 그래서 같은 변수를 한 번 빌렸다가 그 빌림이 더 이상 쓰이지 않으면, 같은 스코프 안에서 다시 빌릴 수 있다.

5.5NLL — 같은 스코프에서 가변/불변 교차 빌림

불변 빌림 r1이 더 이상 안 쓰이는 시점부터 가변 빌림이 시작된다. 예전 같으면 에러였을 코드가 NLL 덕분에 컴파일된다.
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("불변 빌림: {} {}", r1, r2);
    // 이 시점부터 r1, r2는 더 사용되지 않음 → 빌림 종료 (NLL)

    let m = &mut s;     // 가변 빌림 OK
    m.push_str(", world");
    println!("가변 빌림 후: {}", m);
}

5.6NLL이 없으면 에러였을 패턴

루프 안에서 불변 빌림 → 사용 → 가변 빌림. NLL 덕분에 가능하다.
fn main() {
    let mut v: Vec<String> = vec![
        String::from("a"),
        String::from("b"),
        String::from("c"),
    ];

    // 불변 빌림으로 길이 읽기
    let n = v.len();
    println!("len = {}", n);
    // n은 더 안 쓰임 → 불변 빌림 종료

    v.push(String::from("d"));   // 가변 빌림 OK
    println!("{:?}", v);
}
NLL이 중요한 이유 자바 개발자가 Rust에서 "왜 이게 에러야?" 라고 가장 자주 만나는 패턴이 NLL 이전의 빌림 충돌이다. 현재 Rust는 사용 지점까지만 추적하므로 직관에 가깝게 동작한다. 그래도 헷갈리면 "마지막 사용 지점" 을 떠올리면 된다.

5.6 재빌림 (Reborrow) — &mut *x

&mut String을 받은 함수가 그것을 또 다른 함수에 &mut로 넘기는 패턴. 단순해 보이지만 소유권을 옮긴 게 아니라 재빌림이다. 컴파일러가 거의 자동으로 처리하지만, 왜 자동인지를 알아두면 빌림 충돌을 만났을 때 답이 보인다.

5.7암묵적 reborrow와 명시적 reborrow

컴파일러의 자동 처리와 직접 표기.
fn add_bang(s: &mut String) { s.push('!'); }

fn shout(s: &mut String) {
    // 둘 다 작동 — 자동 reborrow
    add_bang(&mut *s);   // 명시적 reborrow (&mut *s)
    add_bang(s);          // 컴파일러가 알아서 &mut *s로 reborrow

    // 핵심: 위 두 호출이 끝나면 s는 다시 "온전한 &mut"으로 돌아온다
    s.push_str(" ZZZ");
}

fn main() {
    let mut greeting = String::from("hi");
    shout(&mut greeting);
    println!("{}", greeting);   // "hi!! ZZZ"
}
왜 reborrow가 필요한가 &mut T는 Copy가 아니다. 그냥 add_bang(s)로 넘기면 소유권 이동인데, 그러면 다음 줄 s.push_str에서 s를 못 쓰게 된다. 컴파일러는 이 상황을 알아서 &mut *s(임시 reborrow)로 변환한다 — 호출이 끝나면 s 사용권이 돌아온다.

Part 6. 라이프타임 생략 3규칙

fn first_word(s: &str) -> &str 같은 함수에 'a가 안 보이는 이유는 컴파일러가 자동으로 채워주기 때문이다. 그 규칙이 정확히 세 가지다. 이 규칙으로 라이프타임이 결정되지 않으면 직접 명시해야 한다.

#규칙
1각 입력 참조에 서로 다른 라이프타임을 부여한다.
2입력 참조가 정확히 하나뿐이면, 그 라이프타임을 모든 출력에 부여한다.
3입력에 &self 또는 &mut self가 있으면, self의 라이프타임을 모든 출력에 부여한다.

6.1 규칙 1 — 각 입력에 다른 'a

// 원본
fn foo(x: &str, y: &str) -> ?
// 규칙 1 적용 후
fn foo<'a, 'b>(x: &'a str, y: &'b str) -> ?

6.1입력만 있고 반환이 참조가 아닐 때 — 생략 OK

반환 타입이 참조가 아니면 출력 라이프타임 결정 문제가 없다.
// 생략된 형태 — 컴파일 통과
fn print_two(x: &str, y: &str) {
    println!("{} {}", x, y);
}

fn main() {
    let a = String::from("hello");
    let b = String::from("world");
    print_two(&a, &b);
}

6.2 규칙 2 — 단일 입력 → 출력에 전파

// 원본
fn first(s: &str) -> &str
// 규칙 1 적용
fn first<'a>(s: &'a str) -> &str
// 규칙 2 적용 (입력 1개)
fn first<'a>(s: &'a str) -> &'a str   ← 완성

6.2입력이 하나면 출력 라이프타임이 자동 결정

'a 없이 작성해도 컴파일러가 채운다.
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}

fn main() {
    let phrase = String::from("Rust is fun");
    println!("first = '{}'", first_word(&phrase));
}

6.3 규칙 3 — 메서드의 &self 우선

impl Foo {
    fn name(&self, _hint: &str) -> &str { ... }
    //         ↑                       ↑
    //      &'a self 이면         반환도 'a (self의 라이프타임)
}

6.3self가 있으면 반환은 self의 라이프타임

힌트 매개변수 라이프타임이 아니라 self의 라이프타임이 반환에 묶인다.
struct Holder { data: String }

impl Holder {
    fn name(&self, _hint: &str) -> &str {
        &self.data
    }
}

fn main() {
    let h = Holder { data: String::from("backed by self") };
    let hint = String::from("ignored");
    let r = h.name(&hint);   // r은 h를 빌림 (hint가 아님)
    drop(hint);              // hint는 일찍 죽어도 OK
    println!("{}", r);
}

6.4 생략 불가 — 명시 강제

입력이 두 개 이상인데 반환이 참조이고 self가 없으면, 어느 입력의 라이프타임을 써야 할지 컴파일러가 알 수 없다. 직접 써줘야 한다.

6.4생략하면 에러 (E0106)

의도된 에러. 메시지에 "missing lifetime specifier"가 보일 것이다.
// 'a 없이 작성 — 컴파일 에러
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let a = String::from("hi");
    let b = String::from("hello");
    println!("{}", longest(&a, &b));
}

6.5 메서드에서 self가 아닌 라이프타임 명시

규칙 3이 적용되면 self의 라이프타임이 자동으로 반환에 묶인다. 만약 self가 아닌 다른 입력의 라이프타임을 반환에 묶고 싶다면, 그 라이프타임을 직접 명시해야 한다.

6.5self가 아닌 input의 라이프타임을 반환에 묶기

'b를 명시해서 input의 라이프타임이 반환에 묶이게. self는 메서드 호출 후 바로 drop되어도 반환값은 input 만큼 산다.
struct Parser;

impl Parser {
    // self의 라이프타임이 아닌 input의 'b를 반환에 묶는다
    fn first_word<'b>(&self, input: &'b str) -> &'b str {
        input.split_whitespace().next().unwrap_or("")
    }
}

fn main() {
    let s = String::from("hello world");
    let w;
    {
        let p = Parser;
        w = p.first_word(&s);
    } // p는 여기서 drop되어도 w는 s 만큼 살아남는다
    println!("first = '{}'", w);
}

7.7 분산 (Variance) — covariant vs invariant

Part 7.5의 "긴 'a를 짧은 'b 자리에 쓸 수 있다"는 사실은 covariance의 한 사례다. Rust 라이프타임 변환 규칙을 정확히 알면 라이프타임 추론이 막힐 때 답이 보인다.

왜 invariant? &mut를 통해 내부 ref에 더 짧은 라이프타임의 값을 쓸 위험이 있기 때문 (메모리 안전성 위반 가능).

7.7covariant — &T는 라이프타임을 줄일 수 있다

&'static T를 &'a T 받는 함수에 그대로 넘길 수 있다.
fn takes_short<'a>(_: &'a str) {}

fn main() {
    let global: &'static str = "I live forever";
    takes_short(global);   // 'static → 'a 자동 변환

    let owned = String::from("owned");
    let local: &str = &owned;
    takes_short(local);    // 일반적

    // Vec<&'a T>도 covariant — 'static 들어있는 Vec을 'a Vec으로 줄여서 사용 가능
    let v: Vec<&'static str> = vec!["a", "b", "c"];
    fn print_all<'a>(items: &Vec<&'a str>) {
        for s in items { print!("{} ", s); }
        println!();
    }
    print_all(&v);
}

7.8invariant — &mut T는 라이프타임 변환 불가 (의도된 에러)

&mut &'static str는 &mut &'a str 자리에 안 들어간다.
// 함수는 &mut &'a str 받음
fn store_short<'a>(slot: &mut &'a str, value: &'a str) {
    *slot = value;
}

fn main() {
    let mut global: &'static str = "first";

    // 같은 스코프 안의 짧은 라이프타임 값
    let temp = String::from("temp"); // <- 'a (main 안)
    let local: &str = &temp;

    // 다음 줄은 컴파일 에러:
    //   global을 &mut &'a str로 reborrow 하려고 함
    //   → 'static을 'a로 *변형* 하는 것은 invariant 위반
    store_short(&mut global, local);
    println!("{}", global);
}
Variance 한 줄 요약 &T는 covariant (자유롭게 줄임), &mut T는 T에 대해 invariant (정확 일치), fn(T) -> U는 T contravariant·U covariant. 자세한 표는 Rustonomicon — Subtyping 참고.

Part 8. 'static

'static은 "프로그램 전체 기간 동안 유효함"을 뜻한다. 두 가지 의미가 있고, 둘이 헷갈리지 않게 구분해야 한다.

형태의미예시
&'static T참조가 'static 동안 유효리터럴 &'static str
T: 'static타입 안에 'static이 아닌 참조가 없음String, i32, Box<str>

8.1 리터럴은 &'static str

8.1리터럴의 진짜 타입

8.2 두 의미 구분

String은 T: 'static 이지만 &'static String은 아니다. String 안에 다른 참조가 없으니 타입 자체는 'static 바운드를 만족하지만, 그 인스턴스 자체는 보통 지역 변수라 영원하지 않다.

8.2T: 'static과 &'static T 의 차이

where T: 'static 바운드는 "타입이 참조를 빌리고 있지 않다"는 뜻일 뿐, 인스턴스가 영원하다는 뜻이 아니다.
fn takes_static_bound<T: 'static>(_: T) {
    println!("T: 'static OK");
}

fn main() {
    takes_static_bound(42_i32);                  // i32: 'static
    takes_static_bound(String::from("hello"));   // String: 'static (내부 참조 없음)
    takes_static_bound(vec![1, 2, 3]);           // Vec<i32>: 'static

    // 반면 빌림이 들어가면 'static 만족 못 함
    // let s = String::from("hi");
    // takes_static_bound(&s); // 에러: &String의 라이프타임이 'static이 아님
}

8.3 String::leak — 런타임에 'static 만들기

이건 거의 안 쓰지만 알면 좋다. 런타임에 만든 String을 의도적으로 &'static str로 누출시킨다. 메모리는 회수되지 않으니 신중히.

8.3String::leak으로 'static 만들기 (Rust 1.72+)

fn main() {

}

8.4 'static 바운드 함정

스레드(spawn)는 F: Send + 'static 바운드를 요구한다. 클로저가 빌림을 캡처하면 'static을 못 만족해 컴파일 에러가 난다.

Part 9. Cow, AsRef, 실전 패턴

현실 코드에서 가장 자주 보는 문자열 추상화 세 가지를 묶었다.

9.1 Cow<'a, str> — Clone-on-Write

"입력을 변경할 필요가 없으면 빌리고, 필요하면 그때만 복제한다". String과 &str의 절충안. 대표 사용 사례: str::to_uppercase 같은 변환을 사용자에 따라 적용할 때, 변경이 없는 경우엔 굳이 새 버퍼를 할당하지 않는다.

9.1Cow — 필요할 때만 할당

탭이 없으면 빌림 그대로 반환, 있으면 새 String 만들어 반환.
use std::borrow::Cow;

fn normalize(input: &str) -> Cow<'_, str> {
    if input.contains('\t') {
        Cow::Owned(input.replace('\t', "    "))   // 할당 발생
    } else {
        Cow::Borrowed(input)                      // 할당 없음 (빌림 그대로)
    }
}

fn main() {
    let a = "no tabs here";
    let b = "with\ttab\there";

    let na = normalize(a);
    let nb = normalize(b);
    println!("a: '{}' (borrowed? {})", na, matches!(na, Cow::Borrowed(_)));
    println!("b: '{}' (owned?    {})", nb, matches!(nb, Cow::Owned(_)));
}

9.2 AsRef<str> — "문자열 비슷한 것" 모두 받기

String, &str, Box<str>, Cow<str>, &String ... 어떤 것이든 받고 싶을 때. impl AsRef<str>가 정답.

9.2AsRef<str>로 다 받기

하나의 함수, 여섯 가지 호출.

fn main() {

Rc<str> / Arc<str> — 공유 소유 문자열

여러 곳에서 같은 문자열을 들어야 할 때, String::clone은 매번 힙 복사가 발생한다. Rc<str>(단일 스레드) / Arc<str>(멀티 스레드)을 쓰면 clone이 카운터 증가만 — 데이터는 한 번만 할당된다. 불변이라 가변 변경은 불가.

9.7Rc / Arc로 cheap clone

카운터를 직접 확인해본다.
use std::rc::Rc;
use std::sync::Arc;

fn main() {
    // Rc — 단일 스레드 공유
    let s: Rc = Rc::from("shared data");
    println!("count = {}", Rc::strong_count(&s));    // 1
    let s2 = Rc::clone(&s);
    let s3 = s.clone();                                // 같은 효과
    println!("count = {}", Rc::strong_count(&s));    // 3
    println!("s = '{}', s2 = '{}', s3 = '{}'", s, s2, s3);

    // Arc — 멀티 스레드
    let a: Arc = Arc::from("thread shared");
    let a2 = Arc::clone(&a);
    let handle = std::thread::spawn(move || {
        println!("스레드: {}", a2);
    });
    handle.join().unwrap();
    println!("메인  : {} (count={})", a, Arc::strong_count(&a));
}
언제 String, 언제 Arc<str> 자주 clone하고 변경 안 한다 → Arc<str> (또는 Rc<str>). 가변 변경 → String. 가변 + 공유가 둘 다 필요하면 Arc<Mutex<String>> (성능 비용 큼).

FromStr / parse::<T>() — 문자열 파싱

"42".parse::<i32>() 같은 패턴의 메커니즘. parse는 str::parse의 메서드인데 내부적으로 T: FromStr 트레이트를 호출한다. 자신만의 타입에 FromStr를 구현하면 같은 문법으로 파싱 가능. 

pub trait FromStr: Sized {
    type Err;
    fn from_str(s: &str) -> Result<Self, Self::Err>;
}

9.8표준 타입 + 사용자 정의 타입 파싱

i32, f64, 그리고 Point 직접 구현.
use std::str::FromStr;

#[derive(Debug)]
struct Point { x: i32, y: i32 }

impl FromStr for Point {
    type Err = String;
    fn from_str(s: &str) -> Result {
        let parts: Vec<&str> = s.split(',').collect();
        if parts.len() != 2 {
            return Err(format!("'{}' is not 'x,y'", s));
        }
        let x = parts[0].trim().parse::().map_err(|e| e.to_string())?;
        let y = parts[1].trim().parse::().map_err(|e| e.to_string())?;
        Ok(Point { x, y })
    }
}

fn main() {
    // 표준 타입
    let n: i32 = "42".parse().unwrap();
    let f: f64 = "3.14".parse().unwrap();
    println!("n = {}, f = {}", n, f);

    let bad: Result = "not a number".parse();
    println!("bad   : {:?}", bad);

    // 사용자 정의
    let p: Point = "10, 20".parse().unwrap();
    println!("point : {:?}", p);

    let bad_p: Result = "10".parse();
    println!("bad p : {:?}", bad_p);
}

Borrow<str> — HashMap 키 lookup의 비밀

HashMap<String, V>에 map.get("apple")처럼 &str로 조회가 가능한 이유. 이게 작동하지 않으면 매번 "apple".to_string()으로 키를 만들어야 한다 (할당 발생). String: Borrow<str> 구현 덕분이다.

9.9HashMap에서 &str 키로 조회

String 키 맵을 &str로 조회 — 할당 없음.
use std::collections::HashMap;

fn main() {
    let mut map: HashMap = HashMap::new();
    map.insert("apple".to_string(), 1);
    map.insert("banana".to_string(), 2);
    map.insert("cherry".to_string(), 3);

    // 셋 다 동일하게 작동, 셋 다 새 String을 만들지 않음
    println!("'apple'  : {:?}", map.get("apple"));         // &str 직접
    let key: &str = "banana";
    println!("'banana' : {:?}", map.get(key));             // &str 변수
    let owned = String::from("cherry");
    println!("'cherry' : {:?}", map.get(&owned));          // &String → &str

    // 이게 가능한 이유:
    // pub fn get(&self, k: &Q) -> Option<&V>
    //     where K: Borrow, Q: Hash + Eq
    // 그리고 impl Borrow for String 이 표준 라이브러리에 있음
}

Part 10. 자주 만나는 에러

라이프타임 관련 에러는 처음엔 어렵지만, 사실 같은 패턴 열 개가 반복될 뿐이다. 각 코드를 실행해보면 컴파일러가 정확히 어떤 메시지를 내는지 확인할 수 있다.

E0106 — missing lifetime specifier

참조를 반환하는데 어느 입력의 라이프타임을 따라야 할지 추론 불가.

10.1E0106 — 입력 두 개, 'a 누락

의도된 에러.
fn longer(a: &str, b: &str) -> &str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    println!("{}", longer("hi", "hello"));
}

E0597 — borrowed value does not live long enough

참조가 가리키는 값이 참조보다 먼저 죽음.

10.2E0597 — 안쪽 변수의 참조를 바깥까지

의도된 에러.
fn main() {
    let r;
    {
        let inner = String::from("temp");
        r = &inner;
    } // inner drop
    println!("{}", r); // 죽은 값 참조
}

E0515 — returns a reference to data owned by current function

함수 안에서 만든 값의 참조를 반환.

10.3E0515 — 댕글링 반환

의도된 에러. 라이프타임을 명시하지 않으면 E0106이 먼저 보이므로 'static을 적어 E0515를 정확히 유도한다. 해결: 참조 대신 String을 반환.
fn make() -> &'static str {
    let s = String::from("local");
    &s
}

fn main() {
    println!("{}", make());
}

E0716 — temporary value dropped while borrowed

임시값(rvalue)을 빌렸는데 그 표현식 끝에서 임시값이 사라짐. 가장 자주 만나는 에러 중 하나.

해결: 임시 String을 변수에 먼저 바인딩하면 그 변수의 라이프타임만큼 산다.

10.4E0716 — 임시 String의 참조 저장

String::from("x").as_str() 결과만 저장해두려고 하면 임시 String이 즉시 죽는다.
fn main() {
    let r: &str = &String::from("temp"); // String은 이 문장 끝에서 drop
    println!("{}", r);                    // 댕글링
}
해결 임시값을 변수에 먼저 바인딩하라. let owned = String::from("temp"); let r: &str = &owned; 로 바꾸면 통과.

E0502 — cannot borrow as mutable because also borrowed as immutable

불변 빌림과 가변 빌림이 동시에 존재.

10.5E0502 — 불변/가변 충돌

불변 빌림 r이 println 이후까지 살아있는 동안 가변 push 시도 → 충돌.
fn main() {
    let mut s = String::from("hello");
    let r = &s;          // 불변 빌림 시작
    s.push_str(", world"); // 가변 빌림 시도 → 충돌
    println!("{}", r);     // r이 여기서도 쓰이므로 NLL 적용 안 됨
}

E0507 — cannot move out of borrowed content

빌린 자리에서 소유권을 빼내려 함.

10.6E0507 — 빌림 통해서 move 시도

해결: .clone() 또는 std::mem::take.
struct Holder { name: String }

fn take_name(h: &Holder) -> String {
    h.name  // 빌림(&h)을 통해 name(String, !Copy)을 move하려 함
}

fn main() {
    let h = Holder { name: String::from("x") };
    let n = take_name(&h);
    println!("{}", n);
}

E0382 — use of moved value

이미 소유권이 이동한 변수를 또 쓰려고 함.

10.7E0382 — move 후 재사용

해결: clone()이나 빌려서 넘기기.
fn consume(s: String) { println!("받음: {}", s); }

fn main() {
    let s = String::from("once");
    consume(s);
    consume(s); // 두 번째: s는 이미 move됨
}

E0521 — borrowed data escapes outside of function

지역 라이프타임이 'static을 요구하는 자리에 들어감. 자주 등장: 스레드, 콜백, 트레이트 객체.

10.8E0521 — thread::spawn에서 빌림 캡처

해결: move 또는 Arc로 공유.
use std::thread;

fn main() {
    let s = String::from("borrowed");
    let handle = thread::spawn(|| {
        println!("{}", s);   // s를 빌림으로 캡처 → 'static 안 됨
    });
    handle.join().unwrap();
}

자동 추론 실패 — 명시가 필요

입력이 여러 개이고 자기 자신을 가리키는 참조를 반환할 때, 컴파일러가 어떤 'a를 따라야 할지 못 정함.

10.9여러 입력 라이프타임 명시 필요

의도된 에러. 입력 두 개 + 참조 반환 + self 없음 → 명시 필요.
struct Pair { a: String, b: String }

// 'a 없이는 컴파일 안 됨
fn pick(p: &Pair, hint: &str) -> &str {
    if p.a.contains(hint) { &p.a } else { &p.b }
}

fn main() {
    let p = Pair { a: "rust lang".into(), b: "ruby lang".into() };
    println!("{}", pick(&p, "rust"));
}

소유와 빌림 동시 보관 시도 (자기 참조 구조체)

구조체 안에 String과 그것을 가리키는 &str를 동시에 두는 것은 안전한 Rust로는 불가능. 이 패턴이 필요하면 Rc, Pin, 또는 인덱스(usize)로 우회.

10.10자기 참조 구조체는 만들 수 없다

의도된 에러. Parsed가 자기 안의 raw를 가리키려 함.
struct Parsed<'a> {
    raw: String,
    head: &'a str,  // raw의 일부를 가리킨다고 가정
}

fn make() -> Parsed<'static> {
    let raw = String::from("hello world");
    let head = &raw[..5];
    Parsed { raw, head } // raw를 move하는 순간 head는 무효
}

fn main() {
    let p = make();
    println!("{} | {}", p.raw, p.head);
}
자기 참조 우회법 ① 인덱스로: head: Range<usize> 만 저장하고 사용 시 &self.raw[range.clone()]. ② ouroboros / yoke 크레이트: 자기 참조 매크로 지원. ③ Rc<str>로 데이터 공유.

10.11 자기참조 우회 — 인덱스 패턴 실제 구현

10.10에서 만들 수 없었던 "원본 + 그 일부를 가리키는 참조" 구조체. &str 대신 Range<usize>를 저장하면 깨끗하게 해결된다.

10.11Range 저장으로 자기참조 깔끔하게

10.10이 안 되는 패턴을 인덱스로 해결.
use std::ops::Range;

struct Parsed {
    raw: String,
    head: Range,
    rest: Range,
}

impl Parsed {
    fn new(s: String) -> Self {
        let split_at = s.find(' ').unwrap_or(s.len());
        let head = 0..split_at;
        let rest = if split_at < s.len() { (split_at + 1)..s.len() } else { 0..0 };
        Parsed { raw: s, head, rest }
    }

    fn head(&self) -> &str { &self.raw[self.head.start..self.head.end] }
    fn rest(&self) -> &str { &self.raw[self.rest.start..self.rest.end] }
}

fn main() {
    let p = Parsed::new(String::from("hello rust world"));
    println!("head = '{}'", p.head());
    println!("rest = '{}'", p.rest());

    // 라이프타임 매개변수가 없으므로 함수 간 자유롭게 이동 가능
    fn returns_parsed() -> Parsed {
        Parsed::new(String::from("first second"))
    }
    let p2 = returns_parsed();
    println!("p2.head = '{}'", p2.head());
}
왜 이게 작동하는가 Range<usize>는 단순 숫자 두 개 — 참조가 아니므로 라이프타임 매개변수가 필요 없다. 슬라이스는 메서드 호출 시점에 &self.raw[range]로 만들어내고, 그 결과는 &self의 라이프타임 안에서만 산다. 자기참조의 "문제"가 사라진다.

Part 11. 트레이트 객체와 라이프타임

Box<dyn Trait> 같은 트레이트 객체는 라이프타임 매개변수가 따라붙는다. 명시하지 않으면 컴파일러가 채워주는 기본값이 있는데, 그 기본값이 의외라서 혼란을 준다.

11.1 Box<dyn Trait> 기본 라이프타임은 'static

Box<dyn Trait>는 Box<dyn Trait + 'static>의 단축형이다. 그래서 박스 안의 객체는 참조를 캡처하지 않는 자기 완결형이어야 한다.

11.1기본 'static 바운드

String은 'static 바운드를 만족하므로 OK.
use std::fmt::Display;

fn boxed_displayable(s: String) -> Box<dyn Display> {
    Box::new(s)   // String: 'static 만족
}

fn main() {
    let b = boxed_displayable(String::from("hi"));
    println!("{}", b);
}

11.2 빌림을 박싱하려면 + 'a 명시

11.2&str을 박싱 — 'static 없으면 에러

의도된 에러. &str가 'static이 아닐 수 있는데 기본은 'static 요구.
use std::fmt::Display;

fn boxed(s: &str) -> Box<dyn Display> {
    Box::new(s)   // s의 라이프타임이 'static이 아니라서 에러
}

fn main() {
    let owned = String::from("hi");
    let b = boxed(&owned);
    println!("{}", b);
}

11.3+ 'a 명시로 해결

Box<dyn Display + 'a>로 라이프타임 바운드를 풀어줌.
use std::fmt::Display;

fn boxed<'a>(s: &'a str) -> Box<dyn Display + 'a> {
    Box::new(s)
}

fn main() {
    let owned = String::from("hi");
    let b = boxed(&owned);
    println!("{}", b);
}

11.3 &dyn Trait — 참조 형태 트레이트 객체

&dyn Trait의 기본 라이프타임은 Box<dyn Trait>와 다르다. 참조의 라이프타임을 따른다.

11.4&dyn Trait — 참조의 라이프타임 따라감

아무 'static 없이도 동작.
use std::fmt::Display;

fn print_via_dyn(x: &dyn Display) {
    println!("{}", x);
}

fn main() {
    let owned = String::from("via &dyn");
    print_via_dyn(&owned);

    let n: i32 = 42;
    print_via_dyn(&n);
}

Part 12. HRTB — for<'a>

Higher-Ranked Trait Bound. "어떤 라이프타임이 와도 만족하는 트레이트"를 표현한다. 클로저를 함수 매개변수로 받을 때 가장 자주 등장한다.

12.1 클로저와 라이프타임 — 왜 HRTB가 필요한가

Fn(&str) -> usize 를 받는 함수를 만들면, 호출자는 &str의 라이프타임을 모른다. 클로저는 호출되는 시점마다 다른 라이프타임의 &str를 받을 수 있어야 한다. 그것이 for<'a> Fn(&'a str) -> usize 의 의미다.

12.1클로저를 받는 함수 — 암묵적 HRTB

사실 Fn(&str) -> usize는 컴파일러가 for<'a> Fn(&'a str)로 자동 확장한다.
fn apply<F>(f: F) -> usize
where F: Fn(&str) -> usize    // 암묵적 for<'a> Fn(&'a str) -> usize
{
    let s1 = String::from("short");
    let s2 = String::from("a bit longer");
    f(&s1) + f(&s2)
}

fn main() {
    let total = apply(|s| s.len());
    println!("total len = {}", total);
}

12.2 for<'a> 명시

실제로 HRTB를 직접 써야 하는 경우는 드물지만, 트레이트 별칭이나 함수 포인터 타입에서 등장한다.

12.2for<'a>를 명시한 함수 포인터

두 표현은 동일하다.
// 두 시그니처는 같다
type Mapper1 = for<'a> fn(&'a str) -> &'a str;
type Mapper2 = fn(&str) -> &str;   // 컴파일러가 위로 확장

fn identity(s: &str) -> &str { s }

fn run(f: Mapper1, x: &str) {
    println!("{}", f(x));
}

fn main() {
    let s = String::from("HRTB!");
    run(identity, &s);
}

12.3HRTB가 진짜 필요한 경우 — where 절

클로저가 어떤 라이프타임으로든 호출 가능해야 함을 명시.
fn each_borrowed<F>(items: &[String], f: F)
where F: for<'a> Fn(&'a str) -> usize
{
    for item in items {
        let len = f(item.as_str());   // &String → &str 명시
        println!("'{}' → {}", item, len);
    }
}

fn main() {
    let items = vec![String::from("a"), String::from("bb"), String::from("ccc")];
    each_borrowed(&items, |s| s.len());
}
한 줄 요약 fn f(s: &str)를 받는 모든 자리는 사실 HRTB가 작동 중이다. 거의 항상 컴파일러가 자동으로 처리해주므로 for<'a> 를 직접 쓸 일은 라이브러리 작성자가 아닌 한 드물다.
